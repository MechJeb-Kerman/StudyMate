## 六行解完汉诺塔

汉诺塔的题面是这样：三根柱子 A、B、C，A 柱上从下到上按大小顺序摞着 $n$ 个盘子，大的在下。每次只允许移动一个盘子，且任何时刻大盘都不能压在小盘上面。要求把 $n$ 个盘子整体搬到 C 柱。

$n = 64$ 时，移动步数是 $2^{64} - 1$，约 $1.8 \times 10^{19}$ 步。把每一步都显式列出来，在数量上就不可能。

下面这段代码只有六行，它给出了完整的移动顺序：

```python
def hanoi(n, a, c, b):
    if n == 0:
        return
    hanoi(n - 1, a, b, c)
    print(f'盘{n}：{a} -> {c}')
    hanoi(n - 1, b, c, a)
```

取 $n = 3$，把这段代码跑一遍，输出是：

```text
盘1：A -> C
盘2：A -> B
盘1：C -> B
盘3：A -> C
盘1：B -> A
盘2：B -> C
盘1：A -> C
```

七步，与 $2^3 - 1 = 7$ 相符。函数体里没有循环，没有列表，也没有别处保存中间状态；它只是调用了自己两次。

一个函数调用自己，居然能把每一步都做完——这一课要把这件事讲清楚，讲清它的代价，以及它在什么地方会崩。

::: note 这一课的位置
上一课讲了栈只在同一端进出。这一课回答的问题是：一个函数调用自己的时候，这种「后进先出」发生在机器的哪一处。树、分治、动态规划的代码骨架全部写成递归，这一课的机制没弄明白，后面每一课都会在同一个位置卡住。
:::

## 递归的三个要素

「递归」的英文是 recursion，源自拉丁语 recurrere：`re-` 表示「回」，`currere` 表示「跑」，字面意思是「往回跑」。

设一个函数的定义里出现了对自身的调用，则称这个函数是**递归函数**，这种定义方式称为**递归定义**。

一个能停下来的递归由三件事构成：

| 要素 | 含义 | 汉诺塔里的对应 |
| --- | --- | --- |
| 基例 | 不再调用自身的那些输入 | `n == 0` 时直接 `return` |
| 递归关系 | 把规模为 $n$ 的问题归结为规模更小的问题 | 把 $n$ 个盘子拆成「$n-1$ 个搬到中转柱、搬第 $n$ 个、$n-1$ 个搬去目标柱」 |
| 向基例收敛 | 每一步递归都让输入严格变小 | 每次调用里 $n$ 减一，有限步后必然到 $0$ |

基例是三者里唯一不能省的一项。它允许有两条或更多（例如 $n = 0$ 与 $n = 1$ 各一条），前提是覆盖所有会终止的分支。

汉诺塔的递归关系值得单独看一眼。要把 $n$ 个盘子从 A 搬到 C：先把上面 $n-1$ 个搬到 B，再把第 $n$ 个（此时它上面已经空了）搬到 C，最后把 $n-1$ 个从 B 搬到 C。这三步里，前一步与后一步都是同一个问题的更小规模，中间那一步是一次直接移动。

按这个关系数一下步数：设 $T(n)$ 为搬 $n$ 个盘子的步数，则 $T(n) = T(n-1) + 1 + T(n-1) = 2T(n-1) + 1$，且 $T(0) = 0$。依次代入得 $T(n) = 2^n - 1$。$n = 64$ 时就是前面那个 $1.8 \times 10^{19}$。

## 调用栈里留下了什么

上一课讲过，栈是只在一端进出的结构，最后压进去的最先被取出。函数调用正是用栈实现的：每发生一次调用，解释器就把一张**栈帧**（stack frame）压到调用栈的栈顶。栈帧里存着这次调用的形参与局部变量，以及一项容易被忽略的内容——**这一层返回之后，控制权交回上一层的哪一行**。

函数返回时，栈顶那张帧被弹出，控制权交回帧里记下的那一行。

由此得到两条结论：

- 栈里同时存在的帧数，就是当前的**递归深度**。
- 最后压入的那层最先返回。这与上一课「后进先出」是同一条规则。

栈帧里的「返回到哪一行」是理解递归返回路径的关键。同一段代码被调用多次，每次进入时执行到哪、返回后接着执行哪，靠的是每张帧各自记一份，而不是靠某处的一个全局标记。

这条性质也解释了递归的一个代价：**每进入一层就多一张帧，帧里的局部变量各存一份**。递归深度越大，占用的内存越多。

## 亲手推一遍两层

把上面的代码加一层缩进打印，栈的进出就变成可见的输出：

```python
def hanoi_trace(n, a, c, b, depth=0):
    pad = '    ' * depth
    print(f'{pad}进入 hanoi({n}, {a} -> {c})')
    if n == 0:
        print(f'{pad}返回：n 为 0，什么都不做')
        return
    hanoi_trace(n - 1, a, b, c, depth + 1)
    print(f'{pad}移动 盘{n}：{a} -> {c}')
    hanoi_trace(n - 1, b, c, a, depth + 1)
    print(f'{pad}返回 hanoi({n}, {a} -> {c})')

hanoi_trace(2, 'A', 'C', 'B')
```

```text
进入 hanoi(2, A -> C)
    进入 hanoi(1, A -> B)
        进入 hanoi(0, A -> C)
        返回：n 为 0，什么都不做
    移动 盘1：A -> B
        进入 hanoi(0, C -> B)
        返回：n 为 0，什么都不做
    返回 hanoi(1, A -> B)
移动 盘2：A -> C
    进入 hanoi(1, B -> C)
        进入 hanoi(0, B -> A)
        返回：n 为 0，什么都不做
    移动 盘1：B -> C
        进入 hanoi(0, A -> C)
        返回：n 为 0，什么都不做
    返回 hanoi(1, B -> C)
返回 hanoi(2, A -> C)
```

缩进的格数就是递归深度。挑几行对一下栈里的内容：

| 输出行 | 深度 | 栈里自底向顶 |
| --- | --- | --- |
| 进入 hanoi(2, A -> C) | 0 | hanoi(2) |
| 进入 hanoi(1, A -> B) | 1 | hanoi(2) · hanoi(1) |
| 进入 hanoi(0, A -> C) | 2 | hanoi(2) · hanoi(1) · hanoi(0) |
| 返回：n 为 0，什么都不做 | 2 | hanoi(2) · hanoi(1) |
| 移动 盘1：A -> B | 1 | hanoi(2) · hanoi(1) |
| 返回 hanoi(1, A -> B) | 0 | hanoi(2) |

这里能看到基例的实际作用：`hanoi(0, ...)` 什么也不做就返回，它的存在是为了让「$n-1$ 个盘子」这件事在 $n = 1$ 时有个终止处。每一次「进入」后面都必然跟着一次同层的「返回」，两者配对出现，数量相等。

## 三个函数与循环版

递归不只在移动盘子上用。下面两个函数是同一件事的两种写法：

```python
def fact_rec(n):
    if n <= 1:
        return 1
    return n * fact_rec(n - 1)

def fact_loop(n):
    r = 1
    for i in range(2, n + 1):
        r *= i
    return r

print(fact_rec(10), fact_loop(10))
```

```text
3628800 3628800
```

求和也一样，再加上第三种写法：

```python
def sum_rec(xs):
    if not xs:
        return 0
    return xs[0] + sum_rec(xs[1:])

def sum_loop(xs):
    s = 0
    for x in xs:
        s += x
    return s

def sum_stack(xs):
    st = [(0, 0)]
    total = 0
    while st:
        i, acc = st.pop()
        if i == len(xs):
            total = acc
            continue
        st.append((i + 1, acc + xs[i]))
    return total

a = [3, 1, 4, 1, 5, 9, 2, 6]
print(sum_rec(a), sum_loop(a), sum_stack(a))
```

```text
31 31 31
```

三个结果一致。三种写法里只有第一种是递归，第三种把「还没处理到哪」与「已经累加到多少」显式地压进了自己维护的栈——它做的是解释器在递归版里替你做的事。

两种写法在代价上并不对等，这一点值得说清：

| 写法 | 时间 | 额外空间 | 说明 |
| --- | --- | --- | --- |
| `sum_loop` | $O(n)$ | $O(1)$ | 只用一个累加变量 |
| `sum_stack` | $O(n)$ | $O(n)$ | 栈里最多存 $n$ 项 |
| `sum_rec` | $O(n)$ | $O(n^2)$ | 每层都写 `xs[1:]`，第 3 课讲过切片会复制一份新列表 |

第三行是这一节最该记住的一条：递归版看起来最短，代价却最高。`xs[1:]` 每进入一层就复制一次剩余全部元素，$n$ 层加起来是 $O(n^2)$ 次复制。

## 缺了基例会怎样

把基例删掉，函数里只剩递归关系：

```python
def broken(n):
    return n + broken(n - 1)

print(broken(5))
```

跑它的现场是这样（中间重复的行省略）：

```text
  File "broken.py", line 2, in broken
    return n + broken(n - 1)
               ~~~~~~^^^^^^^
  [Previous line repeated 996 more times]
RecursionError: maximum recursion depth exceeded
```

报错的名字说明了原因：`broken(5)` 调用 `broken(4)`，再调用 `broken(3)`，`n` 一路减下去却永远不会停，因为没有任何一条输入能让它不调用自己。栈里堆到解释器允许的上限，解释器就把它掐断。

`[Previous line repeated 996 more times]` 这一行给出的是层数。加上最外几层，总数正好是解释器允许的上限。

::: warn 基例覆盖不全，与没有基例同一种后果
只有一条 `if n == 1` 的基例、却用 `n = 0` 去调用时，`n` 会继续减到负数，同样一路调用下去。写基例时要想的是「所有会终止的输入」，不只是最常用的那一个。递归关系不向基例收敛（例如 `broken(n - 1)` 写成 `broken(n)`）也是同一种崩法。
:::

::: quiz 排错 锚点：基例漏掉边界值导致的无限递归
:::

## 递归深度有上限

这个上限是可以查的：

```python
import sys
print(sys.getrecursionlimit())
```

```text
1000
```

本机（Python 3.14.7，free-threading 构建）实测：默认上限 1000，实际能进入的最深层数是 998（本机实测、非通用值，换机器换版本都会变）。它与上面报错里的 `996` 是同一件事的不同侧面。

上限用 `sys.setrecursionlimit()` 可以调高。调高之前要看两件事：

- **栈帧要占内存。** 深度 $10^5$ 的递归，即使上限允许，帧本身占的空间也相当可观。
- **上限受解释器栈空间限制。** 调到远超实际可用的值，程序可能在抛 `RecursionError` 之前就异常退出，那种崩溃不会给你一行可读的报错。

::: warn 调高上限不是解决办法
递归深度随 $n$ 线性增长、而 $n$ 达到 $10^4$ 以上时，正确的做法是把它改写成循环加显式栈（像 `sum_stack` 那样），或者改写成深度只有 $O(\log n)$ 的形状（分治就是这样，后面会讲）。把上限调到一万只是把撞墙的位置往后挪，规模再大一次照样撞。
:::

## 指数级的递归陷阱

有些递归不只是慢，它会随规模指数级地变慢。斐波那契数列的朴素递归就是一个典型：

```python
calls = 0

def fib_rec(n):
    global calls
    calls += 1
    if n < 2:
        return n
    return fib_rec(n - 1) + fib_rec(n - 2)

def fib_loop(n):
    x, y = 0, 1
    for _ in range(n):
        x, y = y, x + y
    return x
```

两个函数都正确，代价差得极远。把调用次数和耗时数出来（计时用第 2 课的 `time.perf_counter()` 前后相减）：

```python
import time

for n in (20, 25, 30):
    calls = 0
    t0 = time.perf_counter()
    v = fib_rec(n)
    t1 = time.perf_counter()
    print(n, v, calls, f'{t1 - t0:.6f} 秒')
```

本机跑出来的三行是：

| $n$ | 递归版调用次数 | 递归版耗时 | 循环版耗时 |
| --- | --- | --- | --- |
| 20 | 21 891 | 0.001483 秒 | — |
| 25 | 242 785 | 0.016244 秒 | — |
| 30 | 2 692 537 | 0.175716 秒 | 0.0000074 秒 |

$n$ 每增加 5，调用次数约乘 11。把 $n$ 从 20 加到 30，规模只增加一半，调用次数却从两万涨到两百七十万——这是指数级增长的形状。$n = 30$ 时循环版是 0.0000074 秒，递归版是 0.175716 秒，相差约 23 700 倍（本机实测、非通用值）。

按这个倍率往下估：$n = 45$ 时递归版约需 $0.175716 \times 11^3 \approx 234$ 秒，$n = 50$ 时约 43 分钟。这道题在 $n = 45$ 上就已经越过了常见的一秒时限。

## 递归改成循环与栈

任何递归都能改写成循环加显式栈，`sum_stack` 就是一个例子。改写的一般形状是：

- 递归函数里的**参数**变成栈里的一项；
- 「调用自己」变成**压入一项**；
- 「返回」变成**弹出并处理**，把这一层的结果并进上一层。

这样写出来的版本深度不再受解释器上限约束，代价是代码更长、可读性更低。

::: quiz 改造 锚点：把递归求和改成显式栈
:::

## 这一课用到的判断

- **写递归先写基例。** 基例要覆盖所有会终止的输入，不只是最常用的那一个。
- **递归关系必须向基例收敛**，每一步都让输入严格变小。
- **每层调用在栈里留下一张帧**，帧里存形参与局部变量、以及返回到哪一行；栈里同时存在的帧数就是深度。
- **深度是有上限的**。本机默认 1000、实测最深 998；深度随 $n$ 线性增长时要考虑改写。
- **调用有一笔固定开销**。第 4 课实测过：空循环 8.5 纳秒、调用一个空函数 22.9 纳秒，两者之差约 14 纳秒就是一次调用的净开销（本次复测 8.39 与 21.83 纳秒，差值 13.44 纳秒，与上一课一致）。递归把调用次数放大，这笔开销也一起放大。
- **一个函数调用自己两次以上时，先估调用次数。** 输入只差常数的那种写法很容易变成指数级。
