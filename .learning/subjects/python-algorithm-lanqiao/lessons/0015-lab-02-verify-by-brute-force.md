## 对拍的四个部件

**对拍**（stress test）由四件事组成，缺一件都跑不起来：

| 部件 | 做什么 | 这一课里对应什么 |
| --- | --- | --- |
| 参照解 | 慢但一定对的解法，作为「标准答案」 | `brute_find`：从头到尾线性扫一遍，一眼看得出对不对 |
| 候选解 | 要验的那一版，快但可能有错 | `buggy.py` 里的 `cand_find` |
| 数据生成器 | 每次造一组新输入 | `gen_wide` 与 `gen_boundary` |
| 比对循环 | 跑两边、比结果、不一致就报告 | `stress` |

参照解为什么用暴力版而不是另一份优化版？因为暴力版**简单到能一眼看出对不对**。它的价值不在快，在于可信：用它当尺子，量出来的差异才有意义。

比对循环的返回值要设计好——不能只回一句「有问题」，要把**那一组数据**一起交回来：

```python
def stress(candidate, reference, gen, trials, seed=None):
    if seed is not None:
        random.seed(seed)
    for t in range(1, trials + 1):
        a, x = gen()
        got = candidate(a, x)
        want = reference(a, x)
        if got != want:
            return t, a, x, got, want
    return None
```

`t` 是第几次抓到的。`seed` 用来固定随机序列——这一点后面单独讲。

## 一个真跑出来的例子

参照解与候选解这样写：

```python
def brute_find(a, x):
    for i in range(len(a)):
        if a[i] == x:
            return i
    return -1

def cand_find(a, x):
    lo = 0
    hi = len(a) - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] == x:
            return mid
        if a[mid] < x:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
```

`cand_find` 就是第 14 课那个「闭区间配上 `while lo < hi`，漏掉最后一个元素」的错法。数据生成器给两组：

```python
def gen_wide():
    n = random.randint(1, 8)
    a = sorted(random.sample(range(100), n))
    return a, random.randrange(100)

def gen_from_array():
    n = random.randint(1, 8)
    a = sorted(random.sample(range(100), n))
    return a, random.choice(a)
```

拿 `gen_from_array` 对拍，第 2 次就抓到了：

```text
第 2 次抓到：a=[63, 97] x=97 候选=-1 参照=1
```

两个元素的数组里，`97` 明明在下标 1 上，候选解却交回 `-1`。原因回到第 14 课那句话：区间只剩一个元素时循环已经退出，那一格从没被检查过。

抓到了不等于看清了。两格的数据已经足够小，但「最小化」这一步仍然值得做——后面单独讲。

## 抓错快慢差四百倍

换成另外三种造数据方案，同一个候选解、同样 5000 次的预算，抓到它的速度差得很远：

| 造数据方案 | 第几次抓到 | 抓到时的那组数据 |
| --- | --- | --- |
| A 宽范围随机（`n` 取 1 到 8，`x` 在 0 到 99 里随便取） | 第 13 次 | `a=[24, 36, 38, 63, 64, 75, 85]` `x=64` |
| B `x` 取自数组元素 | 第 2 次 | `a=[63, 97]` `x=97` |
| C 小值域多重复（值域 0 到 4） | 第 1 次 | `a=[0, 2, 4]` `x=0` |
| D 含空数组与单元素，`x` 仍宽范围随机 | 第 398 次 | `a=[95]` `x=95` |
| E 主动造边界形态，`x` 也按形态给 | 第 1 次 | `a=[72]` `x=72` |

最快第 1 次，最慢第 398 次——**四百倍的差距**。这个结果值得停一下：方案 A 看起来「最随机」，却排在中游；方案 D 明明已经包含单元素数组这种最容易出错的数据形态，却排在最慢。

原因在触发条件。这个候选解只在「答案恰好是最后剩下那个没被检查的元素」时出错。于是抓到它的快慢取决于两件事：

- `x` 得**真的在数组里**。方案 A 里 `x` 在 0 到 99 里随便取，而数组只有几个元素，多数时候 `x` 根本不在数组里——两边都交回 `-1`，一次也抓不到。方案 B 把 `x` 限定成数组里的元素，命中率立刻上去。
- 数组得**有重复值，或者答案在端点**。方案 C 值域只有 0 到 4，重复多，对撞的路径更容易走到「只剩一格」那一步。

方案 D 与方案 E 的对比最能说明问题。两者都包含单元素数组，写法上的差别只在 `x`：

```python
def gen_boundary():
    kind = random.randrange(4)
    if kind == 0:                      # 空数组
        return [], random.randrange(100)
    if kind == 1:                      # 单元素，x 就取那个元素
        v = random.randrange(100)
        return [v], v
    if kind == 2:                      # 全相同
        v = random.randrange(5)
        return [v] * random.randint(2, 6), v
    n = random.randint(2, 6)           # 答案在两端
    a = sorted(random.sample(range(100), n))
    return a, (a[0] if random.randrange(2) == 0 else a[-1])
```

D 里 `x` 仍然宽范围随机，单元素数组必须**恰好**配上 `x` 等于那个元素才会暴露，两个条件叠起来的概率很低；E 里 `kind == 1` 那一支直接把 `x` 设成那个元素，两个条件被绑在一起造出来：

```text
第 1 次抓到：a=[72] x=72 候选=-1 参照=0
```

::: warn 「随机造数据」不等于「能抓到 bug」
随便写一个 `random.randint` 不叫造数据。造数据的目的是**踩中候选解出错的那个条件**，所以要先问一句：这个 bug 在什么输入下才会露出来？答案在边界上（空、一个元素、全相同、答案在两端）时，就把这些形态直接写进生成器，而不是等随机去撞。
:::

所以 `gen_boundary` 的任务很明确：把空数组、单元素、全相同、答案在两端这些形态**主动造出来**，而不是靠随机碰。

::: quiz 理解 锚点：对拍为什么用暴力解当参照
:::

## 反例最小化

抓到的那组数据往往比必要的更大。`a=[63, 97]`、`x=97` 里的第一个元素对暴露 bug 毫无贡献——真正的错在「区间只剩一格」这一步。

**反例最小化**（shrinking）就是反复试着把反例改小，只要它还能让两边不一致，就接受这个更小的版本：

```python
def shrink(candidate, reference, a, x):
    cur = list(a)
    changed = True
    while changed:
        changed = False
        for i in range(len(cur)):
            smaller = cur[:i] + cur[i + 1:]
            if candidate(smaller, x) != reference(smaller, x):
                cur = smaller
                changed = True
                break
    return cur
```

对上面那组反例跑一遍：

```text
原始反例: [63, 97] x = 97  候选 -1  参照 1
最小化后: [97] x = 97  候选 -1  参照 0
```

一步就缩到了极限：一个元素的数组，`97` 就是它自己，候选解却交回 `-1`。看到这一组，错在哪几乎不用再猜了。

最小化之后的反例还有一个用处：它可以**直接抄进测试用例**。第 14 课那些边界数据，其中几条正是这样来的——从对拍抓到的反例里缩出来的。

## 参考解也会错

对拍有一个前提容易被忽略：**它比对的是两个解，不是解与真相**。参照解自己写错时，对拍给出的结论会误导人。

先看一种情况：参照解用了「严格大于」，候选解用了「不小于」。

```text
参照用「严格大于」时：第 1 次抓到 a=[2, 5, 8, 9] x=9 候选=3 参照=4
```

对拍报了不一致。可是**该改哪一边**？对拍自己不知道——它只负责报差异。这时要靠手算的小样例或标准库来裁决：这道题问的是「第一个不小于 `x` 的位置」，正确答案是 3，错的是参照解。

再看更麻烦的一种：两边错成同一种。

```python
def ref_gt(a, x):
    for i in range(len(a)):
        if a[i] > x:
            return i
    return len(a)

def cand_gt(a, x):
    lo = 0
    hi = len(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if a[mid] <= x:
            lo = mid + 1
        else:
            hi = mid
    return lo
```

一个用暴力、一个用二分，写法完全不同，但两边问的都是「第一个严格大于 `x` 的位置」。拿去对拍：

```text
2000 次里不一致的次数: 0 -> 全部通过
```

2000 次全部通过。而真正的答案要求「不小于」：

```text
a=[1, 3, 5] x=3:  两边给 2   真实答案 1
a=[2, 5, 8, 9] x=9:  两边给 4   真实答案 3
a=[1, 1, 1] x=1:  两边给 3   真实答案 0
```

三组全错。**对拍说没问题，实际上两边一起错。** 这也正是「参考解要写得简单到一眼能看出对不对」的原因：复杂到看不出对错的参照解，对拍的全部结论都不可信。

::: warn 对拍通过只说明两版一致
它说明不了任何一版是对的。补上这一条的办法有两个：一是拿**手算过的小样例**（三五个元素那种）钉住答案，二是把参照解写得足够笨——笨到能一眼看出它确实在回答问题。
:::

::: quiz 排错 锚点：参考解自己写错导致对拍失效
:::

## 种子与复现

对拍脚本里如果用了随机数，就必须能复现。看三行输出：

```text
seed=1: 第 2 次抓到 a=[63, 97] x=97
seed=1: 第 2 次抓到 a=[63, 97] x=97
seed=2: 第 1 次抓到 a=[11] x=11
不设种子那一次: 第 1 次抓到 a=[21, 32, 39, 77, 85, 94] x=32
```

同一个 `seed` 连着跑两次，抓到的是**同一组**数据；换个种子就换一组；不设种子则每次都不同。

为什么非要固定种子？因为抓到反例之后你要做的是改代码、再跑一遍确认修好了。不固定种子的话，第二遍跑的是另一批随机数据，它可能根本不碰那个已经修好的位置——于是「改完就通过了」这件事什么都没证明。固定种子之后，同一个反例每次都重现：修之前必挂，修之后必过。

::: warn 不设种子的对拍脚本没法当证据
它的结论只在「刚才那一次运行的随机序列」上成立，别人（包括几小时之后的你）重跑一遍可能得到另一个结果。把 `seed` 写进脚本、也写进记录里，反例才是可复现的证据。
:::

::: quiz 排错 锚点：不固定随机种子导致反例无法复现
:::

## 怎么算过

`run_tests.py` 按四层判：

| 层 | 查什么 |
| --- | --- |
| 第 1 层 | `brute_find` 在几组已知数据上给出正确下标 |
| 第 2 层 | `stress` 拿同一个函数当候选与参照时，跑若干次都交回 `None`（没有自己骗自己） |
| 第 3 层 | `stress` 对拍 `buggy.py` 时能抓到，而且同一个 `seed` 两次抓到同一组 |
| 第 4 层 | `shrink` 的结果仍然让两边不一致，且再也缩不动；`findings.md` 里记的最小反例与判分算出的相同 |

退出码：四层都过是 0，还有没过的（或跳过的）是 1。

第 2 层值得解释一句：拿**同一个函数**同时当候选与参照，对拍必须一次都抓不到。这一层专门抓「`stress` 根本没在比对」这类问题——比如漏了 `if got != want` 那一行，或者把两个结果写反了。

## 怎么跑

```sh
py stress.py            # 手动跑一次，看抓到什么
py run_tests.py         # 交判分
```

`py stress.py` 直接输出抓到的反例、最小化结果与 `findings.md` 该写的内容，对着抄进去即可。

::: practice 上手做 | 五个任务按这个顺序做

**第 1 步 · 写参照解。** 在 `stress.py` 里补 `brute_find(a, x)`：从头到尾扫一遍，找到就交回下标，扫完没有就交回 `-1`。写完拿三组小手算的数据验一遍（空数组、一个元素、两个元素）。

**第 2 步 · 写两个造数据器。** `gen_wide()` 造宽范围随机的数据，返回 `(a, x)`，`a` 要**升序**（候选解是二分，无序的数据会让它给出无意义的答案）。`gen_boundary()` 专门造边界形态：空数组、单元素、全相同、答案在左右两端，各占一部分，别只写其中一种。

**第 3 步 · 写比对循环。** `stress(candidate, reference, gen, trials, seed=None)`：设种子、循环 `trials` 次、每次造数据跑两边、不一致就把「第几次 + 那组数据 + 两个答案」一起交回，全一致交回 `None`。写完先用「同一个函数同时当候选与参照」跑一次 `trials=2000`，必须是 `None`。

**第 4 步 · 写反例最小化。** `shrink(candidate, reference, a, x)`：反复试着删掉一个元素，只要还能让两边不一致就接受。写完在抓到的那组反例上跑一次，看它缩到多小。

**第 5 步 · 用它对拍 `buggy.py` 并把记录写出来。** 跑 `py stress.py`，把三样东西写进 `findings.md`：原始反例、最小化后的反例、`buggy.py` 里哪一行导致了它。最后 `py run_tests.py`，哪一层没过就回哪一步。

:::

## 自查清单

- `brute_find` 在空数组、单元素、目标不存在这三种输入上给出的是 `-1` 吗？
- `gen_wide` 交回的 `a` 是**升序**的吗？`gen_boundary` 是不是真的造了空数组与单元素，而不只是换个值域？
- `stress` 拿同一个函数当候选与参照跑 2000 次，交回的是 `None` 吗？
- 同一个 `seed` 连着跑两次，抓到的是同一组数据吗？
- `shrink` 之后那组数据，跑一遍两边还是不一致吗？再试着删掉一个元素，还缩得动吗？
- `findings.md` 里那三样东西都写了吗？（原始反例、最小反例、出错的那一行）
- 三个任务的函数体里有没有留下的调试 `print`？标准输出应当只有脚本要求的那几行。
- `py run_tests.py` 是不是四层全过、退出码 0？

## 最可能卡在哪

**坑一：参照解自己就写错了。** 表现是：对拍报了一堆不一致，改了半天候选解还是不一致。原因是参照解写错时，对拍的两边都在错。**先单独验参照解**：拿三组手算过的小数据（空、一个元素、两个元素）跑它，答案对得上再拿它对拍。

**坑二：只对拍一组数据就收工。** 表现是：跑一次 `trials=10`，看到 `None` 就认为候选解是对的。这一课的数据摆在那儿：同一个 bug，有的方案第 1 次就中，有的要到第 398 次。次数要足够多（几千次），方案要覆盖边界形态。

**坑三：没固定随机种子。** 表现是：把 `seed` 留成 `None` 或者每次跑都换一个数，于是反例记不下来——写完 `findings.md` 再跑一遍，抓到的是另一组数据，判分第 3 层直接不过。

**坑四：造了无序的数据。** 表现是：对拍报了大量不一致，而那组数据本来就不合法（候选解是二分，前提是有序）。生成器里排一次序，或者用 `sorted(...)` 包一层。

按经验，卡住的地方通常是这几个（按出现频率排）：

| 现象或报错 | 一般缺哪一步 |
| --- | --- |
| `stress` 抛出 `TypeError: 'NoneType' object is not subscriptable` | 函数还空着，交回 `None`；先写第 1、2、3 步 |
| 第 2 层「同一个函数当两边也报不一致」 | `stress` 里的比对条件写反了，或者漏了 `if got != want` |
| 第 3 层「5000 次一次都没抓到」 | `gen_wide` 的 `x` 是宽范围随机的，落在数组里的概率太低；用 `gen_boundary`，或让 `x` 取自数组元素 |
| 第 3 层「两次的 seed 抓到不同数据」 | `random.seed(seed)` 写在循环里了，或者只在 `seed is not None` 之外没设 |
| 第 4 层「缩不动但两边一致了」 | `shrink` 接受了一个让两边重新一致的版本；每次接受之前要再比一次 |
| 对拍报的不一致里有一堆「候选 -1、参照 -1」 | 比对条件写成了 `is not None` 之类；要比的是两个答案本身 |
| `IndexError` 出现在 `gen_wide` 里 | `random.sample(range(100), n)` 当 `n` 大于 100 时报错；把 `n` 的上限压到远小于值域宽度 |

## 卡壳顺序

按这五步来，别一上来就问：

1. **读错误信息。** 判分脚本会把它跑出来的报错最后几行贴出来并指到那一行；`TypeError` 与 `IndexError` 往往直接说明是哪个函数还空着。
2. **自己跑一遍。** `py stress.py` 单独跑，看它到底交回了什么：交回 `None` 是没抓到，抛异常是函数没接上。
3. **看 FAIL 行。** 每一行 FAIL 后面写了期望、实际，以及「这一层指向哪一段」。
4. **再对线索。** 抓不到 → 造数据器没踩中触发条件；两次种子结果不同 → 种子没设对；缩完两边一致了 → `shrink` 接受条件写松了。
5. **对照参考解。** 四层都过了再打开 [lab/solutions/](../lab/solutions/) 比一比——重点比「造数据器覆盖了哪些形态」和「`stress` 的返回值设计」，不是比谁的代码短。
